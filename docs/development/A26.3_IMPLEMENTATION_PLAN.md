## Architecture Decisions

1. **Adapter location:** `src/services/tmdb/tmdbAvailabilityAdapter.ts`.
2. **Supporting TMDB service:** `src/services/tmdb/tmdbAvailabilityService.ts` sits between the adapter and `tmdbRequest`. The existing TMDB service layer remains the only seam that touches `tmdbRequest`.
3. **Response contracts:** `src/services/tmdb/tmdbAvailabilityTypes.ts`.
4. **Tests:** `src/services/tmdb/tmdbAvailabilityAdapter.test.ts`.
5. **Exports:** update `src/services/tmdb/index.ts` (the TMDB barrel only) as required by the implementation; no other barrel or public surface changes. For A26.3-S2 specifically, `index.ts` is NOT modified: barrel/export integration is deferred to the later integration/export gate, where it is actually required.
6. **TMDB capability provider key:** `"tmdb"`, used by the adapter capability and the normalized provider result.
7. **Access offering provider keys:** each TMDB provider offering uses `"tmdb:" + provider_id`.
8. **Provider label key:** the offering label key is structurally `"provider.tmdb." + provider_id`; localization resolution is outside A26.3.
9. **Capability flags:** `isBestEffort: true` (availability is enrichment, never authoritative) and `requiresNetwork: true`, with supported media kinds movie and TV and supported regions taken from the A26.1 catalogue.
10. **Region handling:** the region is extracted from TMDB's response `results[region]` for the caller-supplied explicit `AvailabilityRegionCode`. Do not add a TMDB `region` query parameter to the watch-provider endpoint.
11. **Media identity:** obtain the TMDB ID from the existing `ExternalIdType.tmdb` identity data and branch between the movie and TV watch-provider endpoints.
12. **Single shared adapter:** one shared movie/TV adapter serves both media kinds; no per-media-kind adapter split.
13. **Timeout ownership:** no adapter-owned timeout or retry. The existing `createAvailabilityService` owns timeout and orchestration (`queryTimeoutMs`).
14. **Offline behavior:** preserve the existing availability service offline short-circuit; A26.3 must not add its own network lifecycle.
15. **404:** maps to resolved empty availability because the current domain cannot distinguish an unknown TMDB title from no providers for the region.
16. **429:** maps to rate-limited.
17. **5xx:** maps to service unavailable. Other network/timeout failures stay aligned with the existing `ProviderErrorKind` model.
18. **Test seam:** tests mock the TMDB availability service rather than mocking `fetch`; the repository has no `fetch`-stubbing convention.

## Future Hardening Items (Accepted, Non-Blocking)

Both items below were observed during A26.3-S6 and accepted for A26.3 as non-blocking future hardening/architectural considerations. Neither is an S6 failure, and neither is addressed by changing production code or the frozen A26.2 domain during A26.3.

### 1. Missing `results` object in a TMDB payload

- **Observed behavior:** a payload such as `{ id: 603 }` (no `results`) causes a `TypeError` inside the adapter after the TMDB service request returns, because `response.results[region]` is evaluated outside the request-scoped `try/catch`.
- **System behavior:** the existing availability service normalizes the adapter rejection through its `Promise.allSettled`/error-normalization path, so the availability-system result is `verdict: "unknown"`, `resolution: "error"`, provider error kind `"other"`, with zero offerings and zero groups. No uncaught exception escapes and no availability is fabricated.
- **Disposition:** ACCEPTED for A26.3 — not a blocker. Do not add a runtime validator. Future hardening: consider converting payload-shape faults into a provider-neutral error result inside the adapter if a later authorized step establishes that requirement.

### 2. Provider entry without `provider_id`

- **Observed behavior:** a payload such as `results.IN.flatrate = [{}]` produces an offering with `providerKey: "tmdb:undefined"` and `providerLabelKey: "provider.tmdb.undefined"`; no exception is thrown.
- **System behavior:** the offering is derived from the supplied access-type group, so no fabricated availability occurs — only the provider identity is degenerate.
- **Disposition:** ACCEPTED for A26.3 — not a blocker. Future hardening: consider skipping or rejecting unusable provider entries if a later authorized step establishes that requirement. Do not modify the domain model.
